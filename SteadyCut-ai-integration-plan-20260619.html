SteadyCut — AI Shot-Completeness Integration Plan (Tier 2)

Date: 19 Jun 2026. Status: design. Source: BUILD_PLAN.md Tier 2 + v1.1.x field-test findings.

Scroll to the bottom for the plain-words version if the diagrams below make your eyes glaze.

1. Why we need this — the motion-magnitude ceiling

The current pipeline decides cuts from one number per frame: optical-flow magnitude
(how much the picture moved). The v1.1.x field test proved that number can't tell three very
different things apart — they all just look like "motion went up":

  (A) REAL CUT              (B) SUBJECT MOTION         (C) CAMERA MOVE
      should SPLIT              should NOT split            should SPLIT
   motion                    motion                     motion
    │    █                    │     ████                 │     ▄▄▄▄▄
    │    █                    │    ██████                 │   █████████
    │____█______             _│___████████___           _│__█████████___
         ▲                         ▲                          ▲
      hard cut               cups fill frame             whip-pan / dolly
   magnitude: HIGH          magnitude: HIGH             magnitude: HIGH

A single threshold treats all three identically → the false-splits, cut-too-early and
cut-too-late you saw (49/89 usable). T1.5b (the inlier-coherence gate, shipped in v1.1.2)
fixes (B) vs (C). It still can't judge whether a cut contains a complete action — that's
what the AI does.

2. What "shot completeness" actually means

Given a proposed cut [IN, OUT], the AI answers one question: does this window hold one whole
action, or did we clip it? Four possible verdicts:

  complete      ___╱‾‾‾‾‾╲___        IN before the action starts,
                IN         OUT       OUT after it ends           → keep as-is

  extend_tail   ___╱‾‾‾‾‾‾‾|         action still moving at OUT   → push OUT later
                IN        OUT↗

  trim_out      ___╱‾‾╲_______       OUT sits long after the      → pull OUT earlier
                IN        OUT        action already ended

  fragment      ‾‾╲__╱‾‾             IN/OUT land mid-action,       → reject / flag
                 IN  OUT             a piece is missing

The AI returns the verdict plus a suggested better IN/OUT and a one-line reason.

3. Where it slots in — offline first

Build it as a standalone pass over a folder, not wired into the live app. It reads the
proposed cuts the existing pipeline already produces and judges them. Zero risk to the shipping
product; proves the moat for the price of an API call.

   RAW CLIPS
      │
      ▼
   ┌─────────────────────────── EXISTING (unchanged) ───────────────────────────┐
   │  proxy + motion array   →   stable windows + segment_shots                  │
   └────────────────────────────────────────────────────────────────────────────┘
      │   proposed [IN, OUT] per shot  (+ the cached motion array = free signal)
      ▼
   ┌──────────────────────────── NEW · Tier 2 (offline) ────────────────────────┐
   │  T2.1  sampler  →  pick the frames worth looking at, around IN/OUT          │
   │  T2.2  prompt   →  frames + velocity strip + completeness rubric + examples │
   │  T2.3  vision   →  { verdict, suggested_in, suggested_out, reason }          │
   └────────────────────────────────────────────────────────────────────────────┘
      │
      ▼
   M1 NOW:  write a report (CSV/JSON) + optionally an adjusted XML
   M2 LATER: wire the verdict live into the app's cut decision

4. The four build steps

Step Builds Done when
T2.1 Frame sampler Picks ~5–9 frames around the proposed cut (not 3 even ones) Sampled frames visibly span the action boundaries
T2.2 Prompt Frames + velocity-curve strip + rubric + a few hand-picked examples One clip returns {verdict, in, out, reason}

5. T2.1 — the boundary-straddling sampler

Three evenly-spaced frames (what the person-counter uses) tell you nothing about whether a cut
clipped an action. We sample where the velocity curve we already cached carries the signal:
the buffer just outside IN/OUT (did the action start early / run past?), the velocity peaks (the
action itself), and the threshold crossings (where motion starts/settles = candidate boundaries).

   velocity  (the motion array — already in memory, no new I/O)
     │                    ╭╮
     │          ╭╮       ╱  ╲
     │   ╭╮    ╱  ╲     ╱    ╲       ╭╮
     │__╱  ╲__╱    ╲___╱      ╲_____╱  ╲__
        ●    ▲   ▲        ▲        ▲    ●
        │   peak boundary peak  boundary│
     buffer                          buffer
    before-IN                        after-OUT
        └──► proposed IN          proposed OUT ◄──┘

   ●  buffer anchors (just outside the cut)     ▲  velocity peaks + boundary crossings

Plain version: take pictures where something interesting happens near the in/out points,
plus one just before and one just after, so the AI can see if we cut too soon or too late.

6. T2.2 — the prompt

What the model receives, per proposed cut:

   ┌─ PROMPT ──────────────────────────────────────────────┐
   │  • the 5–9 sampled frames (in order, labelled IN/OUT)  │
   │  • a velocity-curve strip  ▁▂▅█▅▂▁  with IN/OUT marked  │
   │  • the completeness rubric (what each verdict means)   │
   │  • 2–3 hand-picked few-shot examples (good + bad)      │
   └───────────────────────────────────────────────────────┘
                          │
                          ▼
   model returns the structured verdict (next section)

The velocity strip matters: it lets the model reason about motion between the frames it can't
see, cheaply.

7. T2.3 — the vision call + verdict schema

{
  "verdict": "complete | extend_tail | trim_out | fragment",
  "suggested_in":  123,
  "suggested_out": 456,
  "confidence": 0.0,
  "reason": "subject lands the jump at f441; OUT at f456 is clean"
}
  • Model: start with a strong vision model (claude-opus-4-8) — for the gate, accuracy first,
    cost later    . Cost optimisation (cheaper model, or only calling uncertain windows) comes after
    the moat is proven.
  • One call per proposed window. Your last run had 89 windows; for the gate you only run 30.

8. T2.4 — the decision gate ⛳

This is the whole point. Don't scale anything until this number exists.

   30 hand-labeled clips ──┐
     (your IN/OUT+verdict)  ├──► compare ──► AGREEMENT %
   AI verdicts ─────────────┘                   │
                                                 ▼
                                    ≥ target ? ── yes ──► green-light Tier 3
                                         │                (scale to 250+, build benchmark)
                                         └─ no ──► fix rubric / sampler, re-run (cheap)

The output is one fundable sentence: "the AI agrees with a human editor X% of the time on where
a shot should be cut, across N clips."

9. Two realities to decide before scaling (not now)

  1. Who pays for inference. A vision call per window costs money + needs a network + an API key.
    - For T2.4 (the gate): you, local, your key, 30 clips. Cheap. No blocker.
    - For shipping to testers (M2): you can't ship your key. Options = their key / a billing
    proxy / a local model. Park it — it's an M2 problem, not a Tier-2-proof problem.
  2. Offline → online. M1 proves it offline (report only). Wiring the verdict into the live cut
    decision is a later step, after the agreement number says it's worth it.

10. Risks & how we de-risk

Risk Mitigation
AI agreement is poor That's why T2.4 is a gate, not a launch — fail cheap on 30 clips
Cost balloons Gate uses 30 clips; optimise model/selective-calling only after proof
Sampler misses the action Validate on one real clip first (you're sending one) before the 30
Scope creep into the app Offline standalone script — the shipping app is untouched

11. The plan, in plain words 🪨

Right now the program decides where to cut using one number: how much the picture moved.
That number can't tell the difference between "the camera cut to a new shot," "a bunch of people
filled the frame," and "the camera did a fast pan." So it makes bad cuts.

We just shipped a fix (v1.1.2) that handles the "people filled the frame" mistake. But the program
still can't answer the real question: "did I cut at a good spot, or did I chop the action in
half?"

So we're going to show an AI a handful of pictures from around each cut — one just before, one
just after, and a few from the interesting bits in between — and ask it: "Is this a complete
action, or did we cut too early/late?" The AI answers with one of four labels and suggests a
better cut.

We build this as a little separate tool first (not inside the app), run it on 30 clips you've
hand-marked, and check how often the AI agrees with you. If it agrees a lot → the idea works,
we scale it up. If not → we tweak it cheaply and try again. The app itself doesn't change until we
know it works.

You send me one tricky clip, I build the picture-picker and the AI question against it so it's
real, not guesswork. The 30-clip test comes after.

That's it: show the AI the right pictures, ask if the cut is good, prove it on a few clips before
trusting it.
