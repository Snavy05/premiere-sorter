Keep/Cut Review — Approach A The measuring instrument that becomes the product. Human verdict is the benchmark — not a computer accuracy %.

SPEC v0 2026-06-24 branch chore/populate-bin-ffmpeg macOS · Premiere · FCP7-XML only

The Benchmark (reframed)

There is no computer accuracy number. You review a real job, deliberately, and your verdict is the score: PASS = you would ship this timeline. FAIL = you would not.

Why this is right, not lazy

Keep-worthiness is taste, and taste varies per person — so a generated "% accuracy" measures the wrong thing and lies. You are the source of truth: if it doesn't pass your review, it won't pass theirs. That is a founder bet, not a proven fact — fine for sale #1, single reviewer. It also dissolves the overfitting trap: with no metric to game, hand-tuned weights are correct, because they're tuned against your repeated human verdict, not a frozen test set.

ponytail: no sklearn, no train/test split, no precision@k harness. The review screen is the eval. ~300 lines of new code, the rest is reuse.

The Score — keep_worthiness()

A transparent weighted sum of normalized signals. Not ML. You can read why any clip ranked where it did, change a number, re-review.

score = w_face   * face_size_norm      # bigger/closer faces = the moment
      + w_people * person_framed_norm   # subject actually in frame
      + w_sharp  * sharpness_norm       # not soft/out of focus
      + w_audio  * audio_energy_norm    # speech/applause/vows = a beat
      + w_stab   * stability_norm       # old objective, now ONE input not THE input

# weights start EQUAL — neutral prior, no signal favored, zero assumption baked in.
# your keep/cut clicks are the ONLY thing that shapes them. no fixed preset.
ponytail: weighted sum, not a fitted model. // ponytail: swap for logistic regression only if hand-weights plateau across 3+ jobs. A model now would be a bug farm tuned to one person's clicks.
Safety rule — the score orders, it never cuts

A low score means shown later in the list, not discarded. Every clip still reaches your eyes; you still make every keep/cut call. So b-roll that scores low (no face, no audio) does not die silently — you see it and keep it. A wrong weight can only reorder the queue, never lose a good clip. That is why no fixed weight preset is dangerous here: the machine throws nothing away.

Multi-shot clips — the original sin, fixed at the right level

One clip file can hold several moments (continuous record: aisle pan → kiss → guests). The review unit is therefore the window, not the file. find_stable_windows already splits a clip into its distinct held moments and _merge_split_windows already collapses over-splits — segmentation machinery exists, we reuse it. The thing that failed before was scoring those windows by stability; here each window is scored by keep-worthiness. Same pivot, one level down. A 3-moment clip becomes 3 review cards; approved windows become subclips (in/out) in the XML.

Stability is demoted, not deleted. The 50% problem was treating stability as the whole objective. Here it's one input among five — a locked-off empty aisle scores high on stab but near-zero on face/audio, so it sinks. The handheld bride entrance is shaky but maxes face/audio, so it floats. That is the pivot, made concrete.

The Verdict Protocol

One real job, one sitting. The only numbers kept are your own clicks counted back — not a computer's opinion, a mirror of your actions, so you can see if a weight change helped.

  • RESCUE count — clips ranked low that you kept. A high rescue count = a signal is missing keepers. Raise the weight that should have caught them.
  • KILL-on-top count — clips ranked high that you cut. = a signal over-values junk. Lower it.
  • PASS / FAIL — would you ship this job's timeline? Binary, yours. That is the benchmark. Rescue/kill counts only tell you which knob to turn for the next run.

Loop: run job → review → read your two counts → nudge one weight → re-run the same job. Stop when you'd ship it. Then point the identical screen at a fresh job — that's the product (C).

Edge Cases

  • Unreadable / corrupt clip — skip, log to verdict jsonl, never crash the job.
  • No face / no audio in a clip — score from remaining signals; do not drop it to the bottom by default (a scenic cutaway is a legit keep).
  • All windows score near-equal (flat signals) — fall back to existing stability order so the screen is never blank or randomly shuffled.
  • Over-segmentation (one moment split into 2 windows) — mild: both cards are keep-able; tune the _merge_split_windows threshold in fast-follow.
  • Under-segmentation (kiss + junk in one window) — the old problem, but on a ~20s window not a 6-min clip: small blast radius. Frame-trim fast-follow tightens it.
  • You quit mid-review — verdict jsonl is append-only; reopening resumes where you left off.
  • Repeated source / overlapping windows — known landmine in the Resolve path (frozen). Confirm xml_assembler.py handles two kept windows from one source file in the Premiere FCP7 dialect before trusting the timeline.
  • 0 approved clips — write no timeline, tell you plainly, don't emit an empty XML Premiere chokes on.

Test Plan

One runnable check per non-trivial piece. No framework, assert-based, runs from __main__.

  • keep_score.py — self-check in __main__: a money-shot feature vector (big face, high audio, low stability) must outrank an empty-aisle vector (no face, silent, max stability). If that assert fails, the pivot is broken.
  • Audio energy — one loud clip vs one silent clip: energy(loud) > energy(silent).
  • Verdict log round-trip — write a session, reopen, assert decisions restored (resume works).
  • Timeline assembly — N approved windows → N events in the XML (lean on existing xml_assembler coverage; add the count assert).
  • Multi-window-from-one-file — one clip with 2 kept windows → 2 distinct subclips, same source path, correct non-overlapping in/out. This is the repeated-source landmine; assert it on the FCP7 path before trusting any multi-shot job.

Scope — In / Out

  • In: per-window keep/cut (review unit = detected window, not file), content-signal sort, review screen, verdict log, FCP7-XML subclip timeline, macOS.
  • Out — deferred: frame-precise in/out trim of a kept window; merge-threshold tuning; a fitted ML model; auto rough-cut (Approach B).
  • Out — frozen: DaVinci Resolve API, Windows builds. Until a paying user demands them.
  • Out — forever: computer-generated accuracy %. Replaced by your verdict, on purpose.
